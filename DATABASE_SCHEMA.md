**Indexes**: `runs_host_idx` (`host_id`), `runs_city_format_idx` (`city`, `format`), `runs_starts_at_idx`
(`starts_at`). No index on `visibility` or `is_draft` alone — `GET /runs`'s draft/private filtering is a
`WHERE` on top of the city/format-indexed scan, not its own indexed path; worth reviewing if Discover
query plans ever show up as slow.

**Not stored**: `going_count` — always `COUNT(*)` over `join_requests` where `status = 'approved'`
(`approvedCounts` in `loaders.ts`), specifically so it can never drift from the requests that back it.

### `join_requests`

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | text | PK | e.g. `req_...` |
| `run_id` | text | `NOT NULL`, FK → `runs.id` | **`ON DELETE CASCADE`** — deleting a run deletes its requests |
| `requester_id` | text | `NOT NULL`, FK → `users.id` | on-delete: no action |
| `message` | text | nullable | |
| `status` | text | `NOT NULL`, enum `pending` \| `approved` \| `declined` \| `withdrawn` | |
| `decline_reason` | text | nullable | present in the API response only when non-null (truly-absent key, not `null`) |
| `created_at` | text | `NOT NULL` | |
| `decided_at` | text | nullable | set when status leaves `pending` |

**Indexes**: `requests_run_status_idx` (`run_id`, `status`) — host's pending-queue reads;
`requests_requester_idx` (`requester_id`) — "my requests" reads.

**Uniqueness (mid-change — see §3 above)**:
- Committed at `HEAD`: `requests_one_active_per_viewer_idx`, a **partial** unique index on
  (`run_id`, `requester_id`) `WHERE status IN ('pending','approved')`. Old withdrawn/declined rows could
  coexist with a fresh row under this design — i.e. multiple rows per (run, requester) over time.
- Working tree (`schema.ts`, migration `0003`): `requests_one_per_viewer_idx`, a **full, non-partial**
  unique index on the same two columns. This changes the data model itself: **at most one row EVER**
  per (run, requester) — reactivating after withdraw/decline now `UPDATE`s that same row in place
  (`onConflictDoUpdate` in `routes/requests.ts`) instead of inserting a new one. `id` becomes a stable
  identifier for "this requester's relationship to this run" for its whole lifetime; declined/withdrawn
  history is overwritten, not retained as a log (API_CONTRACT.md §2's stated reasoning: "my requests"
  should show one row per game, not one per attempt).
  - **Practical effect of this change worth confirming during review**: any code or reporting that
    assumed multiple historical `join_requests` rows could exist per (run, requester) — e.g. counting
    "declined X times" — no longer has that history available once `0003` ships. Grep for any such
    assumption before merging.

## Relationships

```
users (1) ──< hosts ──── (N) runs
users (1) ──< requests ─ (N) join_requests >── (1) runs   [cascade delete from runs]
```

No `attendees` table — an **approved** `join_requests` row *is* roster membership
(API_CONTRACT.md §1/§6: "no separate Attendee resource"). Roster = `SELECT ... WHERE run_id = ? AND
status = 'approved'`.

## Business rules enforced where

| Rule | Enforced | Where |
|---|---|---|
| `going_count` never drifts from approvals | DB read-time aggregation, not a stored counter | `loaders.approvedCounts` |
| Exact address hidden from non-host/non-approved viewers | Application layer (response shaping), **not** row-level | `lib/viewer.ts` field-presence logic |
| Draft runs invisible to non-hosts | Application layer | `loaders.assertRunVisible` |
| Private runs excluded from list, visible by direct id | Application layer (query filter on list, no filter on detail) | `routes/runs.ts` |
| Capacity can't be edited below current `going_count` | Application layer, checked pre-write | `routes/runs.ts:222-225` |
| One join-request relationship per (run, requester) | **DB constraint** (unique index) + app-level fast-path check | `schema.ts` unique index + `routes/requests.ts` pre-check |
| Auto-approve capacity check | Application layer, checked pre-write, race not closed by a DB constraint | `routes/requests.ts:55-58` — note capacity itself has **no DB-level CHECK**, only the join-request uniqueness race is closed at the DB layer |

Worth flagging in review: capacity enforcement on write (auto-approve path) relies on an app-level
`SELECT COUNT` + compare, not a DB constraint — under true concurrency this has the same class of race
the join-request uniqueness fix (§3) was written to close, just not yet closed. If overbooking under
concurrent auto-approve requests matters, this is the next place to apply the same pattern.

## Open questions this schema encodes a default for (API_CONTRACT.md §7)

These aren't bugs — they're product defaults `backend/` picked in the absence of a product-owner answer.
Flag if the answer has since been decided:

- **Private-run access (Q4/Q6)**: unlisted, not access-controlled. No `invite_token` column exists.
  Adding real invite-gating would need a new column/table here.
- **Withdraw vs. back-out (Q1)**: both collapse to `status = 'withdrawn'` — no distinct status or column
  to tell them apart after the fact.
- **Capacity-edit rules (Q5)**: no restriction to draft-only edits — any host can shrink/grow capacity on
  a published, in-progress run down to (not below) current `going_count`.

## Suggested review checklist

- [ ] Decide/commit the `0003` migration (§3) — confirm no code still assumes multiple historical rows
      per (run, requester).
- [ ] Confirm whether auto-approve capacity should get a DB-level guard (CHECK constraint or the same
      partial-unique-index-style trick) instead of relying solely on the app-level pre-check.
- [ ] Confirm `runs.capacity` should stay unrestricted-by-status on edit, per the Q5 default above, or
      whether it should now be scoped to draft-only.
- [ ] Confirm cascade behavior is intentional both ways: `join_requests.run_id` cascades on run delete;
      `join_requests.requester_id` and `runs.host_id` do **not** cascade on user delete (a user delete
      would currently orphan/fail on FK rather than clean up — no user-delete endpoint exists today, so
      this is latent, not exercised).
- [ ] If adding new columns: mirror the change in `API_CONTRACT.md` §2 and `src/contract-types.ts` in
      the same change (per this repo's standing rule), and re-run `npm run db:generate` to produce the
      migration rather than hand-writing SQL.
